topic: First playable gbRythm: one song with falling notes the player hits in time, judged and scored
updated: 2026-10-05T13:03
---


- (direction) User asked for the first playable spec after the dev-environment and music-proof epics closed; guided mode as in the earlier specs (2026-10-05).
- (decision) Why, confirmed by user as drafted: a vision to realize and something to learn; the first time the ROM is a game; one song played start to finish shows whether a rhythm game in C on the Game Boy feels right, before menus, more songs or polish.
- (decision) Five lanes, the user's own design, not an offered option: Left, Up, Right, B, A, mapped to the notes of the song so Left is the lowest pitch and A the highest within one octave; the high D maps to the same lane as the normal D.
- (decision) One falling note per melody note; user chose this over a hand-written step chart. The lane is decided by the note's pitch, so nothing extra is written per song.
- (decision) Presses are graded perfect, good or miss by how close they are in time; user chose graded over hit-or-miss.
- (note) The song's five pitches are D, E, G, A, B, so the mapping is D to Left, E to Up, G to Right, the note A to the B button, the note B to the A button. The note names and button names collide for A and B.
- (decision) The first playable uses the full first verse of Amazing Grace; user chose it over the half verse already in the ROM, so the song is extended as part of this work.
- (decision) When the song ends a results screen shows the perfect, good and miss counts, and Start plays again; user chose this over looping.
- (decision) The player cannot fail: the song always plays through and misses are only counted; user chose this over ending on too many misses.
- (decision) Success signal confirmed by user as drafted; real hardware declined for now.
- (capability) CAP-1: the player starts the song and, as it plays, one note falls for each melody note, in the lane its pitch maps to, reaching the target line as that note sounds.
- (capability) CAP-2: a press of a lane's button is graded perfect or good by how close it is to the note's arrival; a note not pressed in time is a miss; the player sees each judgement.
- (capability) CAP-3: when the song ends the player sees the counts of perfects, goods and misses, and can play again.
- (capability) CAP-4: the song is the full first verse of Amazing Grace.
- (capability) CAP-5: an agent can check the game with no display by playing it with scripted presses.
- (capability) CAP-6: the timing windows are tuned so judgements feel fair to the user.
- (capability) CAP-7: the instructions explain how the game plays and how notes map to lanes, and a rebuild from them still passes.
- (constraint) Inherits the dev-environment and music-proof contracts: GBDK 4.5.0, C, original Game Boy, hUGEDriver 6.1.3, tools in tools/, command-line non-interactive build and check, C rules in stack.md.
- (constraint) Falling notes are derived from the song's own data, never from a second copy of the tune, so notes and music cannot drift apart when the song is edited (follows from one note per melody note; answers the music retrospective's F4 and F8).
- (constraint) Five lanes in the fixed order Left, Up, Right, B, A; a pitch maps to the same lane in every octave; the mapping table is in lane-mapping.md.
- (constraint) The ROM stays 32K or smaller with no mapper, carried from the dev-environment spec; whether the game fits is an open question.
- (constraint) The melody stays a single line on one channel, so the check's note detection still works (music retrospective F11); harmony and drums are out.
- (constraint) The headless check and the user's play in Emulicious are both required; the user's play is the only human step.
- (decision) Non-goals proposed by the agent, not yet confirmed by the user: title screen and menus, more than one song, difficulty levels, held notes and simultaneous notes, points and combos, sound effects, harmony or drums, saving scores, finished art, real hardware.
- (assumption) The game replaces the proof ROM's current screen (text, arrow and note images, A PRESSED); the image route and headless check are reused but the check's expectations are rewritten for the game.
- (assumption) The game waits for Start before the song begins, so the player is ready.
- (assumption) Notes fall from the top to a target line near the bottom of the screen.
- (assumption) A note arriving within two frames of its sound counts as in time for CAP-1; the figure is the agent's, not the user's.
- (assumption) Graphics are simple placeholders made by the agent, as the proof ROM's images were.
- (question) What should a press do when no note is near, or the wrong lane's button is pressed: nothing, or count as a miss?
- (question) How wide are the perfect and good windows to start with? CAP-6 tunes them by play, but the build needs starting values.
- (question) Does the game fit in 32K with the driver, the verse and the graphics? If not, is a mapper acceptable?
- (question) Is C fast enough for five lanes of falling notes with judged input at 60 frames a second? The research flagged timing in C as unmeasured.
- (question) The tune has two eighth notes a third of a second apart; is that playable at the current tempo, or should the tempo drop?
