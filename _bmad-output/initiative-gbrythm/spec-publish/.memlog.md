- (direction) User's idea, 2026-10-05: build the project with a GitHub Action, host a release build on GitHub, and host a web-based emulator in the README. Told that a README cannot run an emulator (GitHub strips scripts and frames) and that a GitHub Pages page linked from the README is the equivalent; the user went ahead with the spec. Guided mode, as in the earlier specs.
- (decision) Why, confirmed by user as drafted: an opportunity; the game builds on one Steam Deck and nobody else can see it; building on GitHub proves the instructions on a machine that has never seen the project, a published ROM lets anyone run it, and a play page lets anyone try it in a browser one click from the README.
- (decision) GitHub builds and checks on every push to main; user chose this over also building pull requests, since work is committed straight to main.
- (decision) A release is published when the user pushes a version tag, with the ROM attached; user chose this over a rolling release on every push.
- (decision) The play page is for desktop browsers with keyboard controls only; user chose this over also supporting phones with on-screen buttons.
- (decision) The play page shows the latest release, not the latest push; user chose this so visitors get a version the user chose to publish and the page matches the downloadable ROM.
- (decision) The repository is public, by the user's statement; GitHub Pages can be used as it is.
- (decision) The project is licensed MIT; user chose this over deciding later or staying unlicensed.
- (decision) Success signal confirmed by user as drafted, with the rule that a failed check publishes nothing; the user declined adding their own play-through on the page as a requirement.
- (capability) CAP-1: every push to main is built and checked on GitHub, on a machine that has never seen the project.
- (capability) CAP-2: pushing a version tag publishes a GitHub Release with the ROM attached.
- (capability) CAP-3: a web page plays the latest release in a desktop browser with keyboard controls.
- (capability) CAP-4: the README links to the play page and the latest release, one click each.
- (capability) CAP-5: the repository carries the MIT licence.
- (capability) CAP-6: the instructions explain how the build, release and play page work and how to publish a release.
- (constraint) A failed build or check publishes nothing: no release and no change to the play page.
- (constraint) GitHub runs the same make commands a person runs, with the tools installed at the versions and checksums docs/setup.md pins; there is no separate build path for GitHub.
- (constraint) The published ROM is the file that passed the check in that run, unchanged; the game is not altered for the web.
- (constraint) The play page is static files on this repository's GitHub Pages: no server, no accounts, no tracking; any third-party emulator is at a pinned version with its licence recorded and compatible with publishing.
- (constraint) Desktop browsers with a keyboard only; the page shows which keys are the five lane buttons and Start.
- (constraint) Pushing, tagging and changing repository settings are the user's actions; the agent prepares files and says what to do, in keeping with the user's standing choice to commit their own work.
- (decision) Non-goals proposed by the agent, not yet confirmed one by one: phones and touch controls; building pull requests; version numbers or changelogs made automatically; scores shared online; a custom web address; more than one emulator; real hardware.
- (assumption) GitHub runs both make check and make check-debug; the user kept them as two commands locally, and running both in the workflow costs seconds.
- (assumption) Version tags look like v0.1.0.
- (assumption) The MIT licence names Wayne Atkinson-Young, the git author, and the year 2026.
- (assumption) Java and Emulicious are not installed on GitHub; only the build and the headless check are needed there.
- (question) Which browser emulator: it must run this ROM correctly, let keys be mapped to six buttons, be embeddable as static files, and carry a licence that allows it. Not yet researched.
- (question) Do the licences of what is built into the ROM, GBDK's library code and hUGEDriver, allow publishing it? hUGEDriver is described as public domain in the research; GBDK's library terms have not been read.
- (question) Does the headless check run unchanged on GitHub's machines? PyBoy is used with no window, but it has only ever run on this Steam Deck.
- (question) How does the game feel in a browser? A browser emulator adds its own delay to keys and sound, and the timing windows were accepted in other emulators.
- (question) GitHub Pages has to be switched on in the repository's settings, by the user; which source it publishes from depends on how the workflow is written.
